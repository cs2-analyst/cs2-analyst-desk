# P7 比赛报告 · 不滚动视图三种布局设计（不实施）

> 2026-10-18 仅评估设计，**不改 `main.tsx` 报告页代码**；等待产品选择具体方案。本页独立于 P7 多楼层 Replay 诊断。目标不是隐藏滚动条，而是让**整个比赛报告视图本身无需纵向滚动**，长内容在明确可见的内部分区滚动/分页，不截断数据。

## 0. 当前布局与不可丢内容

来自 `apps/desktop/renderer/src/main.tsx`：
- 顶部比赛信息（地图、比分、回合、DEM basename）与目标玩家选择器，由共享 `viewHeader` 占位；
- 8 个主要指标卡：K/D/A、ADR、HS%、KAST、Trade rate、Trade kills、Opening、Clutch，tooltip/hint/coverage 保持；
- 下半部左侧 Findings（规则提示、证据展开、查看相关回合、比赛回放联动），右侧“道具与残局”（投掷/伤害 Tab 与残局列表）；
- 加载、错误、coverage warning、无结论、证据不足等状态必须如实显示。

当前报告是 `tabPanel {overflowY:'auto'}` + 一屏排列多个卡片，导致**整视图滚动**。三种方案在 1024×640 / 1920×1032 的真实高度限制下必须可用；不要靠缩小字体到难以阅读掩盖问题。

## 方案 A · 顶部 8 KPI + 下方双列独立滚动（推荐）

```text
┌───────────────────────────────────────────────────────────────────────┐
│ 共享比赛标题 / 当前玩家（各视图共用，保持原样）                      │
├───────────────────────────────────────────────────────────────────────┤
│ [K/D/A] [ADR] [HS%] [KAST] [Trade rate] [Trade kills] [Opening] [Clutch] │
│    紧凑响应式 KPI：宽屏 4×2；窄屏优先 4×2 或横向可读折叠              │
├────────────────────────────────┬──────────────────────────────────────┤
│ Findings                       │ [道具投掷 / 道具伤害]                 │
│                                │ 残局列表                             │
│ 结论卡 1                        │                                      │
│ 结论卡 2                        │ 右列独立滚动                          │
│ ...                            │                                      │
│ 左列独立滚动                    │                                      │
└────────────────────────────────┴──────────────────────────────────────┘
```

- 外层固定为 `flex:1; min-height:0; overflow:hidden`，上方 KPI 区固定适配高度，下方左右栏目各 `min-height:0; overflow-y:auto`。
- KPI 建议优先使用 4×2，不强制 8×1；1024 小窗口尺寸要保证可读。长 tooltip 仍 hover/focus 可用。
- 右列道具和残局可增加局部内页签或内部分区，但不改变现有“投掷/伤害”业务含义。
- **优点**：改动最小、信息全量同屏可定位、优先复盘从进入报告即能看到；易复用旧卡片。
- **缺点**：较矮屏幕下 KPI 区仍占一定高度，双列内容空间可能很窄；两套内滚需清晰边界、保留滚动位置与无障碍。

## 方案 B · 紧凑 KPI + 主内容分组页签

```text
┌───────────────────────────────────────────────────────────────────────┐
│ 共享比赛标题 / 当前玩家                                              │
├───────────────────────────────────────────────────────────────────────┤
│ KPI 1 KPI 2 KPI 3 KPI 4   /   KPI 5 KPI 6 KPI 7 KPI 8                │
├───────────────────────────────────────────────────────────────────────┤
│ [复盘结论] [道具] [残局]                                              │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│                   当前选中页签的完整内容                              │
│                 填满剩余区域、内部滚动 / 横向滚动                    │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

- 8 指标始终固定可见；下方一个大内容区域通过 Fluent Tab 显示 Findings、Utility、Clutch。
- 内容区单个滚动上下文，聚焦自然；不丢掉任何卡片、说明、关联回合动作。
- **优点**：窗口窄、内容多时优先保证正文宽度与阅读舒适度；信息层级清晰。
- **缺点**：用户不再能同时看到 Findings 和道具；多一个 Tab 点击，和独立「分析视图」中 Tab 形态趋同；需防止与原道具“投掷/伤害”双 Tab 造成导航层级混淆。

## 方案 C · 左侧垂直 KPI/模块选择 + 右侧主详情

```text
┌───────────────────────────────────────────────────────────────────────┐
│ 共享比赛标题 / 当前玩家                                              │
├───────────────────┬───────────────────────────────────────────────────┤
│ 关键指标  [4×2]    │ 当前模块：Findings                                │
│ [KDA]   [ADR]     │                                                   │
│ [HS%]   [KAST]    │ 结论详情 / 道具 / 残局（可按选择切换）             │
│ [补枪]  [首杀]    │                                                   │
│ [TRD]   [残局]    │ 主面板填满剩余高度                                │
│                   │ 内部滚动                                          │
│  ───────────      │                                                   │
│ [复盘提示]        │                                                   │
│ [道具统计]        │                                                   │
│ [残局]            │                                                   │
└───────────────────┴───────────────────────────────────────────────────┘
```

- 把 KPI 以较窄但可读的两列网格固定放左侧，左下是局部模块菜单；右侧主卡片根据选择展示长内容。
- **优点**：垂直空间利用率高，报告主内容单独大滚动区；可以适配未来增加统计模块，不影响整体框架。
- **缺点**：宽度要求更高，1024px 整窗减去现有应用 Sidebar 后余宽偏窄；需增加响应式切换方案，迁移成本和视觉改动最大。

## 比较与决策建议

| 维度 | 方案 A 双列 | 方案 B 主内容页签 | 方案 C 仪表盘主从 |
| --- | --- | --- | --- |
| 全部八项 KPI 即时可见 | 是 | 是 | 是 |
| Findings 与道具同屏 | 是 | 否 | 否 |
| 页面级纵向滚动 | 无 | 无 | 无 |
| 内部滚动 | 两栏独立 | 单主区域 | 单主区域 |
| 对当前源码的改造成本 | **低** | 中 | 高 |
| 1024×640 适配风险 | 中 | **低** | 高 |
| 未来信息增加 | 中 | 高 | 高 |
| 设计推荐 | **首选** | 备选（信息较多时） | 非首选 |

**推荐 A**：最符合“保留现有报告能力而减少迁移”的要求；但如果真实 1024×640 下 KPI 占用过大、让结论阅读困难，则转选方案 B。方案 C 暂不推荐，因为应用已有永久左侧导航，双左栏可能拥挤。

## 选择后才允许实施的验收

1. 真实 Electron 1024×640 与 1920×1032；无报告视图级滚动（`scrollHeight<=clientHeight`），所有指标与细节可通过可见分区访问。
2. coverage warning、长昵称/DEM 文件名、极长 Findings、无道具/无残局以及报告失败时不溢出或裁断。
3. 原有 8 项数值、tooltip、证据展开、相关回合/回放动作、道具投掷/伤害 Tab、残局表完全不变。
4. 鼠标、键盘 Tab/方向键/滚轮、屏幕阅读器、Windows 高对比度和 reduced-motion 均可达；只在预期分区内部滚动。
5. 设计确认前不修改 Report JSX/CSS、不标为实施 PASS。
