# 比赛库：使用源 DEM 重新分析

2026-10-25 存储更新：明确重新分析现在写入 archive v2（Brotli、无损 Replay tuple、版本化按需回放）；仍沿用本文 SQLite v3 不可变归档代和提交边界。v1 不会在普通打开或重复导入时自动迁移。兼容及完整性验证见[无损存储优化](./match-library-storage-optimization.md)。

2026-10-25，用户明确授权新增。入口：比赛数据 → 单场记录「更多操作」→「重新分析」。选择这场比赛原始 DEM 后，使用当前安装版本的 Parser、Analytics、Findings、Deep Review、Replay 与 Heatmap 生产链路重新生成完整归档；完成后直接打开新报告。无需先删除比赛记录，不自动批量升级，不保存 DEM 路径或源文件。

## 用户行为与身份

- Main 打开本机 DEM 选择对话框；Renderer 只发送比赛 ID，不接收或提交磁盘路径。
- 以解析所得 `match.id`（源字节 SHA-256）核对原记录。相同文件名不代表同一场；内容不符时拒绝更新，要求选择原录像。Worker、Main 与存储层均核对目标身份。
- 保存的 `selfPlayerId`（「自己是谁」）原样保留，包括尚未选择时的 null；重新分析不弹出身份问题。新解析结果缺少已选玩家时拒绝更新，不静默清空。
- 保留比赛 ID 与原导入时间，更新分析版本、报告、Replay 块及 Heatmap 规范源，清除该场派生摘要缓存。列表仍只有一条记录，重新打开与导出使用最新完整归档。
- 普通 DEM 导入与 `.cs2a` 导入继续保留去重重开语义；只有明确执行「重新分析」才替换已有分析快照。
- 复用现有任务阶段和取消入口，文案区分重新分析与首次导入。选择文件取消、源不匹配、解析失败或提交前取消均保留旧报告、身份、导航和可用会话。

## 提交与恢复

报告/归档 schema 仍为 2/1；SQLite 目录迁移至 v3，增加不跨 IPC 的受校验 `archive_key`。旧记录默认引用 `matches/<matchId>`；更新候选写入全新的 `matches/<matchId>.<staging UUID>`。这改变的是快照引用，每代归档本身仍不可变。

1. Utility 在 staging 生成并逐组件解压验证完整新归档。原记录及旧会话仍保留。
2. `replaceStaging` 再验证候选压缩摘要、目标身份、旧索引与归档一致性、身份及原导入时间。
3. 先将新目录移入比赛区，在短 SQLite 事务中切换归档指针、摘要/版本/大小，并删除玩家派生缓存。事务内没有异步操作；同步提交通知是取消的分界点。
4. 提交前错误或退出会中止候选，旧指针不动。提交后清理旧代失败不会撤销成功，重启再清理。
5. 候选进程在提交后退出时，Main 从已保存的新归档启动恢复进程；若激活仍失败，明确告知「新报告已保存，暂时无法打开」，刷新列表并停用旧 IPC 会话，允许从比赛库重试。
6. 启动先核验所有索引指针、manifest 摘要与快照，再清理没有引用的代。损坏指针会保留该比赛所有代供处理，不把唯一完好的旧归档当作孤儿删除。

迁移兼容 v1/v2 目录及玩家偏好，拒绝未来不受支持的数据库版本。目录键仅允许同一比赛 ID 及生成的 UUID；原有目录重定向、文件链接、预算、受信 frame 和操作互斥保护保持生效。不改变便携 `.cs2a` 格式，不修改核心分析算法或领域契约。
