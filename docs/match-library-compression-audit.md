# 本地分析归档容量与无损优化调查

2026-10-25。范围：调查及离线原型，**没有修改生产压缩格式、分析规则、用户归档或数据库**。机器结果：[JSON](./match-library-compression-audit.json)；可复现工具：`scripts/library-compression-audit.mjs`。原格式及约束见[存储设计](./match-library-storage.md)。

## 1. 结论

当前归档已经是逐成员 gzip level 6。主要占用来自规范回放源、UI 回放块和完整 Spatial 证据，报告及基础 Match 很小。4 份样本中，Brotli-6 在原始 JSON 字节完全不变的前提下，再减少 **14.27%–16.02% 的压缩载荷**，是优先级最高的容量优化候选。

更大的空间来自回放的两种表达：本次所有 **499 个 Chunk** 均可用当前 `Match + MatchReplay` 重建到逐字节一致，4 份 Replay metadata 也一致。但不能直接删除历史 Chunk；当前恢复直接按块读它们，正式改动必须解决版本兼容、随机 seek、冷打开和峰值内存。现阶段只证明当前样本存在约三分之一的可再生派生载荷，未证明它可以零成本移除。

## 2. 当前占用

单位统一为十进制 **MB = 1,000,000 bytes**，为文件逻辑字节，不是 NTFS 物理簇占用。demo1/demo2 来自用户现有比赛库，只读检查清单和成员 SHA；Dust2/Nuke 使用白名单原文件与当前生产 Parser / 报告 / ReplaySession / HeatmapSession / writer 创建临时归档，无 DEM 复制或下载。

| 数据组成 | demo1，24 回合 | demo2，18 回合 | 用途 |
| --- | ---: | ---: | --- |
| 报告 | 0.0276 MB | 0.0208 MB | 统计、Findings、时间线、深度复盘及展示分析 |
| 基础 Match | 0.0804 MB | 0.0499 MB | 事件、回合窗口、名单/边界状态等规范数据 |
| 规范 MatchReplay | 4.3562 MB | 3.1201 MB | 完整采样状态、时序、道具等；位置热力图来源 |
| 完整 Spatial | 4.4135 MB | 2.6261 MB | 事件前/当时/后及边界样本，精确位置/视角/武器/coverage 证据 |
| UI Replay Chunk | 4.3543 MB | 3.1070 MB | 按块随机读取的 UI 帧、事件、道具窗口及跟随信息 |
| manifest | 0.0330 MB | 0.0252 MB | 版本、目录、能力、逐成员大小与摘要 |
| **合计** | **13.2651 MB** | **8.9492 MB** | 不含 SQLite/WAL、目录簇和应用共享素材 |

回放两种表达及 Spatial 合计约占 **98.9%**；单独报告约占 **0.2%**。现场目录的 SQLite + WAL 采样为 296,480 bytes，是整个小目录索引的开销，不是每场重复存储。每场本来就不包含原 DEM、地图 PNG 或武器图标。

跨样本：Dust2 24 回合为 **16.9101 MB**，Nuke 21 回合为 **12.0662 MB**。因此每回合并非固定容量；时长、采样帧数、事件密度等也会改变体积。demo1 与 Dust2 都是 24 回合，容量仍不同。

## 3. 仅更换无损编码

在实际捆绑的 **Electron 44.5.1 / Node 24.21.0**（Windows x64）内逐成员测量，保持现有独立块粒度。515 个成员各用 6 种编码回环，解码结果均与原 JSON 的长度和每个字节一致，当前 gzip-6 大小也与原文件一致。

下表为**压缩载荷**，不含约 25–45 KB 的清单；新 codec 的正式清单尚未冻结，不能把它称作已落盘、可直接读取的新归档。

| 编码 | demo1 | demo2 | Dust2 | Nuke | 相对 gzip-6 的载荷节省 |
| --- | ---: | ---: | ---: | ---: | ---: |
| gzip-6，现状 | 13.2321 MB | 8.9239 MB | 16.8652 MB | 12.0262 MB | — |
| gzip-9 | 12.9938 MB | 8.7626 MB | 16.5641 MB | 11.7761 MB | 1.79%–2.08% |
| Brotli-4 | 11.7457 MB | 7.9871 MB | 15.1844 MB | 10.8460 MB | 9.81%–11.23% |
| **Brotli-6** | **11.1119 MB** | **7.5858 MB** | **14.4588 MB** | **10.1642 MB** | **14.27%–16.02%** |
| Brotli-9 | 10.9675 MB | 7.4958 MB | 14.2776 MB | 10.0520 MB | 15.34%–17.11% |
| Zstd-3 | 13.1853 MB | 8.9747 MB | 16.9937 MB | 12.2405 MB | demo1 小 0.35%；其余反增 0.57%–1.78% |

单轮逐成员编码 CPU 墙钟累计：gzip-6 约 0.68–1.19 秒，Brotli-4 0.51–0.86 秒，Brotli-6 1.01–1.81 秒，Brotli-9 2.48–4.36 秒。解码累计约 0.12–0.29 秒，几种编码处于同一量级。这些是串行暖缓存单次观测，**不是 p95、导入耗时或冷打开 SLA**；没有声称 Brotli 解压一定更快。Zstd-3 编码较快，但本组数据容量收益不足；Brotli-9 相比 6 只多省约 1 个百分点，编码代价明显上升。

## 4. 无损结构表达原型

原型只改变存储表示，所有坐标/视角保留原 JavaScript Number，SteamID 保持字符串，null/false/缺失字段不合并。样本顺序、eventIndex、relation、coverage、fields、武器、遗漏采样信息等均保留。解包后 JSON 字节必须与原成员完全一致，不用浮点容差。

| 原型 | 测量结果 | 判断 |
| --- | --- | --- |
| MatchReplay 对象样本改为带 schema 的 tuple | gzip-6 下每场再省 0.216–0.413 MB，约整档 2.2%–2.5% | 可作为后续小幅优化；增加新编码/解码分支 |
| Spatial 全字段相同样本字典 | 原 JSON 变小，但 gzip-6 后**反增 42–58 KB/场**；Brotli-6 下也没有胜过直接压缩原 Spatial | 不推荐；gzip 已利用了大量重复，索引/字典改变局部重复性会抵消收益 |
| 每回合共享整回合 follow，Chunk 引用后原值恢复 | gzip 载荷省 22–50 KB/场；还未扣新增文件清单，脚本仅另列 256B/项的规划估计 | 收益过小，不值得为此增加读取和缓存复杂度 |
| 保留 Match + MatchReplay，按需再生 UI Chunk | 当前 499/499 Chunk 的长度/SHA、4/4 metadata 完全一致；UI Chunk 本身占整档 32.8%–36.9% | 体积潜力最大，但尚未通过新格式兼容、随机 I/O、冷恢复和内存验收 |

结构原型的字典/schema/ref 头及新增字典 gzip 载荷已经计入；新增正式 manifest 条目、格式版本及迁移方案尚未设计，不能把这些原型载荷节省当成最终净节省。Map 字典和解包也可能增加写入峰值内存，现有 512 MiB Heatmap 准入仍是约束，不因本调查而放宽。

## 5. 不能以容量为由裁掉的内容

- 不降低 8Hz 采样，不合并近似坐标，不改 float32、不四舍五入；否则既有回放和网格边界可能变化。
- 不把完整证据换成默认热力图图片或一个默认网格；玩家、阵营、回合、楼层、冻结时间、采样集及 16/32/64 网格仍要可用。
- 不只保留 Spatial 的 kill/at-event 坐标。即使当前热力图主要消费它们，其他事件/前后文/武器/视角/未知原因仍属于已保存证据。
- 不直接裁掉 Chunk guard 帧、跨块道具轨迹/窗口、盲时、燃烧和跟随状态；它们支撑独立随机定位。
- 不因“当前版本能再生”而删除历史 Chunk。生成过程依赖切块策略、昵称/事件文案、地图楼层和资源版本，需要稳定的版本化编码语义。

## 6. 建议顺序与验收边界

优先研究**保持独立成员粒度的 Brotli-4/6 版本化归档**，在体积、导入 CPU 和读取延迟间选择；本组容量优先候选为 6。旧 v1 的 `gzipBytes` / `gzipSha256` / `.json.gz` 与 gunzip 已写死，不能只替换压缩函数。正式实现需同时覆盖 writer、reader、清单预算/摘要、`.cs2a`、旧档兼容、损坏/取消/中断、真实 Electron 与安装版冷恢复及 seek。

然后才考虑规范 Replay 的 tuple 编码；更大的“只存规范源、按需派生 UI 块”作为独立设计工作。未建议先做 Spatial 字典、follow 小文件或报告瘦身。当前报告已有 Findings 等结果快照，不应为了几十 KB 去改变分析证据或历史结论。

这次保证的是：所有 codec 回环及结构解包对这些真实样本都严格无损，且用户归档内容未改。**没有发布或启用新格式，也没有把 size-only 实验当成完整产品验收。**

## 7. 重现与证据

```powershell
# 当前生产链路生成新的临时容量样本，不写用户比赛库。
node --expose-gc scripts/library-compression-audit.mjs capture .demo/dust2.dem <新的临时结果.json>

# 使用捆绑 Electron 作为 Node 子进程运行 measure / regenerate，不能在 GUI 子系统下未等待就当作完成。
# stdin/stdout 需由宿主 spawnSync 等待，ELECTRON_RUN_AS_NODE=1。
# measure <归档目录> <归档目录之外的新结果.json>
# regenerate <归档目录> <归档目录之外的新结果.json>
```

完整测量输出在本机 `%TEMP%/cs2-compression-audit-42e2efc8af764025867ac9f4d78b3553/`。脚本拒绝覆盖结果、拒绝往被测归档内部写结果；源成员核对大小、压缩/原始 SHA，结束再核对 manifest 未变。所有实验解码均验证原字节一致。capture 使用隔离 Node 26.3.0，并在原样 Heatmap 准入前显式 GC；该步骤只用于容量捕获，不作为生产导入内存或耗时证据。实际 codec/再生比较使用上述捆绑 Electron runtime。

验证结果：脚本语法检查通过，复用的 L0 辅助工具回归 5/5 通过；另以独立进程验证 6 项只读/禁止覆盖/目录 junction 防护，输入目录内容不变。独立只读复审重新核算样本、字节会计、515 成员、499 Chunk 和 metadata，通过。并未穷尽所有 codec 参数或二进制表达；Brotli-6 是本次已测候选中的优先方案，不声称全局最优。
